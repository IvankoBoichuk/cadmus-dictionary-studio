# ADR-0008: AI-генерація схеми статті та provider-порт для structured extraction

- Статус: Accepted
- Дата: 2026-08-26
- Jira: BH-148

## Контекст

BH-148 вимагає, щоб редактор описував структуру словникової статті довільним
текстом (`article_description`), а система на основі цього опису автоматично
виділяла поля статті (заголовне слово, значення, приклади, синоніми,
скорочення, географічні позначки) з provenance для кожного поля
([[ADR-0004]]). Різні словники мають різну структуру статті, тому набір
полів не фіксований у коді — його потрібно виводити з опису конкретного
словника.

Вихідне формулювання задачі в Jira передбачало окрему MongoDB-базу для
статей "оскільки різні словники мають різну схему". Це прямо суперечить
[[ADR-0002]] (Accepted), яка вже відхилила MongoDB як основну БД саме через
слабше вираження критичних зв'язків і ревізій, і обрала PostgreSQL + JSONB
для варіативних payload. Крім того, у кодовій базі ще немає жодної
інтеграції з LLM/AI-провайдером — цей патерн потрібно ввести вперше,
узгоджено з [[ADR-0003]] (provider-neutral pipeline, AI-вивід — це
пропозиція, а не джерело істини).

## Рішення

Схему статті й вивід AI зберігаємо в PostgreSQL, без нової БД:

- `ArticleSchema` — версійована сутність у модулі `lexicography`; поле
  `definition` (дерево полів: назва, role, тип, repeatable/required,
  children) зберігається як JSONB-колонка, а не в окремій БД — це той самий
  підхід, що вже використовується для `changed_fields`, geography
  `geometry` тощо ([[ADR-0002]]). Лише одна версія на словник може бути
  `active` одночасно; попередні версії залишаються як історія.
- `DictionaryEntry` / `EntryFragment` / `EntryField` — реляційні таблиці
  (не JSONB), оскільки кожне поле статті потребує власного provenance
  (`origin`, `confidence`, `source_start`/`source_end`, `processing_run_id`)
  і має бути запитуваним/індексованим окремо. Це поєднання — JSONB для
  гнучкої *схеми*, реляційні рядки для конкретних *екземплярів* полів —
  відповідає формулюванню задачі "canonical JSON/SQL model" без потреби у
  MongoDB.
- Новий `AiSchemaProvider(Protocol)` у `lexicography/ports.py`
  (`generate_schema`, `extract_fields`) — за зразком канонічного
  `OcrProvider`-контракту з `docs/architecture.md` §8. Конкретний адаптер
  `AnthropicAiSchemaProvider` живе виключно в
  `infrastructure/ai_schema.py` ("worker-only boundary", як і
  `infrastructure/ocr.py`) — доменний і application-код не імпортують SDK
  провайдера напряму, лише через порт.
- AI-вивід трактується як пропозиція ([[ADR-0003]], [[ADR-0004]]):
  згенерована схема отримує статус `READY` і активується редактором
  окремою дією; кожне екстраговане поле отримує `origin=model` і
  `confidence`, а ручне редагування переводить `origin` у `manual` зі
  штампом автора/часу. Жоден вихідний текст не видаляється — поле
  зберігається як offset-діапазон (`source_start`/`source_end`) над
  незмінним `EntryFragment.recognized_text`, тож нерозпізнаний залишок
  тексту завжди залишається видимим для рев'ю.

## Наслідки

- Не додається нова БД, не з'являється окремий backup/HA контур для Mongo;
  усе живе в тій самій PostgreSQL-схемі `cadmus` і тому самому
  Alembic-ланцюжку міграцій ([[ADR-0005]]).
- AI-провайдер підключається через `Protocol`, тому його можна замінити чи
  замокати в тестах без зміни domain/application-коду (жоден unit-тест не
  викликає реальний Anthropic API).
- Генерація схеми й екстракція полів — довгі мережеві виклики, тому обидві
  винесені в Celery-задачі за тим самим enqueue/poll патерном, що вже
  використовується для OCR-пропозицій.
- Валідація "канонічної схеми" (AC: "результат проходить перевірку
  канонічної схеми") реалізована як `validate_entry_against_schema` —
  порівняння персистованих `EntryField` з деревом `ArticleSchema.definition`
  перед переходом статті в статус `complete`, а не як окрема JSON Schema
  бібліотека — узгоджено з мінімалістичним підходом решти кодової бази.
- Правило-базоване визначення скорочень і географічних позначок
  (`RuleBasedAnnotationService`) не потребує AI-виклику: воно звіряє текст
  полів із вже наявними `Abbreviation`/`DictionarySettlementMapping` з
  модуля `sources` — дешевше й детерміновано порівняно з делегуванням цього
  також моделі.

## Відхилені альтернативи

- MongoDB як сховище статей (буквальне формулювання задачі): суперечить
  [[ADR-0002]]; довелося б або скасовувати Accepted-рішення без нової
  технічної підстави, або підтримувати другу БД лише заради змінної схеми,
  яку JSONB уже покриває.
- Зберігати екземпляри полів (`EntryField`) теж як JSONB-дерево на
  `DictionaryEntry`, а не окремими рядками: спростило б запис, але
  унеможливило б окреме індексування/фільтрацію за `role`/`origin`/
  `confidence` і зробило б часткові ручні правки (одне поле) складнішими,
  ніж перезапис усього дерева.
- Будувати повний модуль `document` (нормалізовані OCR-блоки/токени) як
  передумову для BH-148: це окремий, більший обсяг роботи за
  [[ADR-0006]]/BH-26; замість цього `lexicography` тимчасово звертається
  напряму до `sources.DictionaryPage` через уже наявний `Lexeme`-шлях, як і
  раніше.
