# Шаблон промпту для виконання Jira Story у Codex

Виконай Jira Story `[JIRA_KEY]`.

## Підготовка

Перед внесенням змін:

1. Прочитай кореневий `AGENTS.md` і всі релевантні вкладені `AGENTS.md`.
2. Отримай повний опис Jira Story `[JIRA_KEY]`, включно з Acceptance Criteria.
3. Прочитай `docs/architecture.md` і релевантні ADR.
4. Проаналізуй поточну структуру репозиторію та пов’язані модулі.
5. Перевір актуальний стан `main` і незмерджені PR, які можуть конфліктувати із задачею.
6. Визнач залежності, ризики й можливі конфлікти.
7. Якщо вимоги суперечать архітектурі або одна одній — зупинись і чітко опиши суперечність.

## Планування

Перед реалізацією склади короткий план, у якому зазнач:

- мету задачі;
- що входить і не входить у scope;
- файли та модулі, які змінюватимуться;
- зміни API або бази даних;
- залежності й ризики;
- план тестування;
- відповідність кожному Acceptance Criterion.

Якщо потрібне важливе продуктове чи архітектурне рішення — покажи план і дочекайся підтвердження. Якщо задача однозначна й відповідає чинній архітектурі — продовжуй реалізацію.

## Реалізація

- Створи гілку `agent/[JIRA_KEY]-<short-description>`.
- Реалізуй тільки scope цієї Story, без суміжних покращень.
- Дотримуйся принципів GRASP і SOLID, але уникай overengineering.
- Не змінюй публічні контракти й архітектурні рішення без прямої потреби.
- Не створюй абстракції, якщо для них немає чіткої відповідальності або точки варіативності.
- Не змінюй семантику `source_text` неявно.
- Зберігай provenance: координати, confidence, версії обробки та історію змін.
- Не додавай секрети, приватні документи, згенеровані артефакти чи локальні volumes.
- Для змін БД додай міграцію та перевір збереження наявних даних.
- Для змін API онови OpenAPI та відповідну документацію.
- Для нових команд розробника онови `README`, `Makefile` або `AGENTS.md`.

## Тести

Додай релевантні тести залежно від характеру задачі:

- unit;
- integration;
- API;
- негативні сценарії та валідація;
- authorization;
- regression;
- idempotency і retry;
- provenance та захист від втрати даних.

Не додавай формальні тести без корисної перевірки поведінки.

## Перевірка

Запусти релевантні команди, визначені в `AGENTS.md`, наприклад:

```bash
make test
make lint
make format-check
make type-check
make verify
```

Запускай лише команди, які реально існують у проєкті. Не стверджуй, що перевірка пройшла, якщо її не запускав. Якщо щось неможливо запустити, вкажи точну причину; не приховуй помилки й не послаблюй перевірки.

## Self-review

Перед публікацією:

1. Переглянь повний diff.
2. Повторно звір зміни з описом Story.
3. Перевір кожен Acceptance Criterion.
4. Переконайся, що немає сторонніх змін.
5. Перевір архітектурні залежності та відсутність небажаних циклів.
6. Оціни cohesion і coupling за GRASP.
7. Перевір безпеку, provenance і ризик втрати даних.
8. Перевір `git status`.
9. Виправ знайдені проблеми.
10. Повторно запусти релевантні перевірки.

## Pull Request

Після успішної перевірки:

1. Закоміть зміни логічним комітом.
2. Запуш гілку.
3. Створи Draft PR у `main`.

Назва PR:

```text
[JIRA_KEY] <короткий опис результату>
```

У PR опиши:

- що змінено і чому;
- що залишилося поза scope;
- виконані перевірки та їх результати;
- відповідність Acceptance Criteria;
- міграції та зміни API;
- відомі обмеження.

## Фінальний звіт

Надай:

- посилання на Draft PR;
- назву гілки;
- перелік змінених файлів;
- запущені команди та результати;
- відповідність кожному Acceptance Criterion;
- відомі обмеження й рекомендовані наступні задачі.

Не мерж PR і не переводь Jira Story у `Done` автоматично.
